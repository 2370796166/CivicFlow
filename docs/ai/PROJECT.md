# CivicFlow 产品范围

## 1. 产品目标

CivicFlow 为城市公共服务网点提供“可预约、可确认、可签到、可排队、可追溯”的统一平台。首版优先解决号源配置、并发抢号、预约确认超时、到店签到和窗口叫号的一条完整链路，并保证库存与预约事实可以对账。

核心价值指标：无超卖、无重复有效预约、预约状态可解释、同一排队票不被两个窗口领取、故障后可补偿/对账、越权请求被拒绝。

## 2. 角色与权限边界

| 角色 | 首版能力 | 明确边界 |
| --- | --- | --- |
| USER 普通用户 | 登录；查网点/事项/号源；抢号；查创建结果；确认/取消；获取签到码；签到；查排队进度 | 只能访问本人预约、二维码和排队票 |
| STAFF 窗口人员 | 登录工作台；选择获授权网点/窗口；开始/结束会话；叫号、重呼、过号、开始办理、完成 | 只能操作授权网点/窗口及其当前会话 |
| ADMIN 管理员 | 管理用户角色、网点、事项、窗口、时间段和号源；触发/查看对账与安全修复 | 高影响写操作需审计；不等于数据库超级用户 |

同一账号可有多个角色；权限以服务端 RBAC 和资源归属共同裁决。

## 3. 核心用例

### 3.1 配置与放号

1. 管理员配置网点、事项、窗口、事项绑定、服务日期/时间段和总号源。
2. resource 数据库是配置事实源；定时任务读取即将放号的 slot 快照并预热 Redis 运行时库存。
3. 放号后额度变更不得直接覆盖 Redis，必须通过带配置版本的增量同步或重建/对账流程。

### 3.2 抢号与建单

1. 应用生成 `reservationId`，网关按用户和 slot 限流。
2. Lua 在同一原子操作内校验 slot、放号时间、库存与用户日事项占用，扣减库存，写预占和用户占用键。
3. 应用用 publisher confirm 发布 `appointment.reservation.requested.v1`。确认失败且重试耗尽后执行幂等补偿 Lua；崩溃留下的未决预占由恢复扫描处理。
4. 消费者至少一次接收，按 `reservationId` 幂等，在 appointment 数据库创建 `PENDING_CONFIRM` 预约和有效占位；唯一约束是最终重复防线。
5. 查询在 Redis 预占成功但订单尚未落库期间展示投影状态 `CREATING`。

### 3.3 确认、取消与超时

- `PENDING_CONFIRM` 的数据库截止时间严格为创建后 5 分钟。
- 用户在截止前用条件更新确认；确认后可获取短期签到二维码令牌。
- 建单事务同时写超时 outbox，发布至 RabbitMQ 5 分钟 TTL 队列，过期经 DLX 进入超时检查队列。
- 超时消费者以数据库时间和 `status=PENDING_CONFIRM` 条件 CAS 为 `EXPIRED`，再幂等释放 Redis 库存与用户占用。确认与超时只能有一方成功。
- 合法取消同样先完成数据库 CAS/释放占位，再通过可重试补偿记录释放库存。

### 3.4 签到与排队

1. `CONFIRMED` 预约在签到窗口内取得短时签名令牌；令牌包含随机 nonce，不是裸 appointmentId。
2. queue 携带 token 调 appointment 内部 claim 接口；appointment 在一次本地事务内校验令牌、预约归属/状态、服务日期、网点、签到窗口与 nonce，并以 CAS 执行 `CONFIRMED -> CHECKED_IN`。它与取消在同一数据库决胜。
3. claim 成功后 queue 为同一 appointment 创建唯一 queue ticket，并可靠回告 ticketId；claim 后建票失败由相同 token/幂等键重试和签到对账补齐，不能回滚成 CONFIRMED。
4. 用户查看排队号、前方人数和当前状态。

### 3.5 窗口办理

1. 窗口人员开启唯一工作会话。
2. 多窗口并发叫下一号时，queue 使用 MySQL 8 `FOR UPDATE SKIP LOCKED` 短事务，按优先级、签到时间、ticketId 稳定领取。
3. 支持重呼、过号、开始办理、完成；状态变化写操作日志并可靠同步预约状态。

### 3.6 对账

按 slot 比较 resource 配置总量、appointment 已消费/已释放事实、Redis 剩余量与未决预占。对账允许短暂最终一致窗口；安全可判定的差异用版本/CAS Lua 修复，不确定差异只记录与告警。

## 4. 首版模块范围

- `civicflow-common`：轻量统一响应、异常、追踪/安全上下文契约与基础工具。
- `civicflow-gateway`：路由、JWT 前置校验、可信头清洗/注入、Sentinel 限流、请求追踪。
- `civicflow-auth`：账号登录、用户/角色、JWT 签发刷新撤销、服务身份令牌。
- `civicflow-resource`：网点、事项、窗口、绑定、排班时间段和号源配置事实。
- `civicflow-appointment`：预热/抢号、异步建单、确认/取消/超时、二维码签发与预约侧对账。
- `civicflow-queue`：签到、排队票、窗口会话、叫号/过号/办理。
- `civicflow-web`：Vue 单应用内的用户端、窗口端、管理端路由与页面。

## 5. 非目标

- 不做支付、退款、短信/邮件/微信通知、评价、推荐、智能预测、地图导航、多租户计费。
- 不做跨城市/跨时区、多语言、无障碍合规认证；但代码不应阻断未来扩展。
- 不引入 DDD、CQRS、事件溯源、Saga 框架、分布式事务或跨库查询。
- 首版不承诺 WebSocket/SSE；排队进度可配置轮询。
- 不将 Redis/RabbitMQ 视为永久事实源，不追求 Redis Cluster 跨 slot 脚本；key 设计已为同一业务分片共槽。
- 不自动修复无法由确定事实推导的库存差异。

## 6. 成功边界

首版完成定义以端到端主链路和故障链路均可验证为准：1000 并发争抢 quota=100 不超卖；单用户同事项同日仅一个有效预约；消息重复不重复建单；确认/超时和取消/超时竞态唯一终态；双窗口不重复领票；二维码篡改/越权/重放不可产生第二张票；对账能解释差异。
